# 技术要点

这份笔记记录的是**实测出来的**结论，不是文档抄来的。每条都对应 `poi_core.py` 里的一段实现。

---

## 一、为什么拿到的总是 500px

高德 POI 检索接口（`show_fields=photos`）返回的图片地址长这样：

```
https://store.is.autonavi.com/showpic/8a1b2c...?operate=merge&w=500&h=375
```

`w=500&h=375` 是 CDN 的缩放参数。**直接下载这两百来 KB，得到的就是 500px 宽的缩略图**——把它放大到 2000px 只会得到一张模糊的假高清，插值填出来的像素没有任何新增细节。

### 还原原图

高德图片存在阿里云 OSS 上（`store.is.autonavi.com` / `is.autonavi.com` / `aos-comment.amap.com`），这类 OSS 图片服务普遍支持**按需实时缩放**，参数形式有多种。实测有效的做法是**追加一条 `x-oss-process`，让 `resize` 与 `limit_1` 成对出现**——这正是 `poi_core.upscale_url()` 的唯一实现：

```python
if "x-oss-process" in url:          # 已带处理参数，原样返回，不重复追加
    return url
sep = "&" if "?" in url else "?"
return f"{url}{sep}x-oss-process=image/resize,w_{width},limit_1"   # width 默认 5000
```

关键在两条参数的分工：

| 参数 | 作用 | 单独使用的后果 |
|---|---|---|
| `resize,w_N` | 目标宽度上限 | 不带 `limit_1` 时，会把 500px 原图上采样到 N 宽——插值填出来的假高清 |
| `limit_1` | 禁止上采样 | 单独使用时语义依 CDN 实现而异，不如成对使用稳定 |

**成对使用**时，`resize` 给出上限、`limit_1` 保证不越过原图：原图宽 1518px 就返回 1518px，不会为了凑 5000 而插值。所以代码里的 `w_5000` 不是"要 5000px"，而是"最多 5000px，超不过原图"。

> **反例**：只追加 `resize,w_4000` 而**不带** `limit_1`。CDN 会照做，把 500px 的缩略图上采样成 4000px 返回，看着尺寸很大，实际全是插值像素，文件还更糊。**resize 必须和 limit_1 一起出现。**
>
> 已有的 `w` / `h` 参数不必手工去除——追加 `x-oss-process` 后由 CDN 按 OSS 处理链解析，实测以 `x-oss-process` 为准。`upscale_url()` 之所以在检测到 `x-oss-process` 时直接返回，是为了幂等：同一 URL 反复处理不会叠出两条参数。

## 二、怎么判断「这真的是原图」

只看 URL 参数不可靠，CDN 也可能本身就是缩略图。可靠的判据是**递增请求宽度、观察实际像素何时不再增长**：

同一 URL 依次请求不同 width，若返回尺寸在某个值之后不再变化，说明已经触到原始分辨率上限，该值即原图尺寸。

实测样本（40 个机构、数百张图）：真实分辨率中位数约 **1518px**，最高 **4000px**；40 个机构全部达到 150dpi 的印刷下限，其中 14 家达到 300dpi。

`poi_core.image_size()` 直接解析图片头字节取宽高（不依赖 Pillow），下载后逐张记录到 `photo_inventory.csv`，避免"以为拿到了原图其实没有"。

## 三、百度：官方接口不给图

百度地图开放平台的 POI 检索接口**不返回图片地址**，只能从**网页版接口**解析：

| 接口 | 用途 | 鉴权 |
|---|---|---|
| `map.baidu.com/?qt=s&wd=<关键词>` | POI 搜索 | 免鉴权 |
| `map.baidu.com/?qt=inf&uid=<UID>` | POI 详情（含相册） | 免鉴权 |
| `map.baidu.com/?qt=pr3d&uid=<UID>` | 全景图 | 免鉴权，**要过滤** |

搜到的 `uid` 拿去请求 `qt=inf`，响应里有 `photo_album` 结构，相册图片地址在其中。

### 百度图片同样是缩略图

百度相册地址形如：

```
https://hiphotos.baidu.com/.../pic.jpg?x-bce-process=image/resize,m_lfit,w_1080,limit_1
```

`x-bce-process` 是百度对象存储（BOS）的图片处理参数，**整段 query 去掉就是原图**。保留 `x-bce-process` 只会拿到 1080px 宽的处理图。

> 注意：百度这条路上**不要**再手工加 `resize`，同高德一样，加了就是上采样假放大。去掉处理参数即可。

### 要过滤的图

- **全景图**：`qt=pr3d` 返回的地址 host 为 `*.bdimg.com` 且带 `qt=pr3d`，是 360° 全景切片，不是门店实景。去掉参数后返回 404。
- **地图切片与图标**：`qt=vtile`、`qt=cen`、`/tile/`、`staticimage`、`/marker/`、`/icon/`、`logo.` 等（见 `poi_core.IMG_DENY_RE`）。

## 四、两源清晰度实测对比

同名机构交叉比对（7 组同名样本）：

| 结果 | 数量 |
|---|---|
| 高德更清晰 | 6 |
| 平手 | 1 |
| 百度更清晰 | 0 |

**结论：高德作主源，百度作补充源。** 百度胜在覆盖（同一区域能搜出更多机构、多出电话字段），高德胜在像素。

一次对照实测（各 20 个机构）：高德 58 张 / 最优中位 1500px；百度 44 张 / 中位 1080px。

## 五、配额与调用成本

高德个人认证账号（实测口径，以官方为准）：

| 项目 | 配额 |
|---|---|
| 基础搜索 | 5,000 次 / 月 |
| 基础 LBS | 150,000 次 / 月 |
| 基础地图定位 | 1,500,000 次 / 月 |

一次 40 个 POI 的采集只消耗 **2 次** 搜索调用（翻页另计），**图片下载不计入配额**（走 CDN，不走 API）。

百度侧网页接口无配额概念，但频率过快会触发限流，`--delay` 别设 0。

## 六、踩过的坑

### 1. `region` 传「省+市」会静默退化为全国搜索

高德接口的 `region` 参数不认「广东省深圳市」这种写法，**不报错**，直接当成没传，返回全国结果。表现为：目录名写着深圳市，清单里却是别的城市的机构。

处理：加城市名规范化（去掉省级前缀），并做一次结果校验——返回机构地址与目标城市不符时报警。

对应实现：`poi_core.normalize_region()` + `region_core()`。

### 2. `max_poi = 0` 被当成「0 个」

原逻辑 `if len(results) >= max_poi: break` 在 `max_poi=0` 时立刻成立，只抓一条就停。

处理：把判断改成 `if max_poi and len(results) >= max_poi`，`0` 明确表示不限制。

### 3. 手机版入口没有更多图

`m.map.baidu.com` 返回 502，`mapsv0` 相册接口 404。逐条核对 `photo_num` 与相册实际项数**完全一致**（5 对 5），据此判定 PC 网页接口已给全量，不必再折腾移动端。

### 4. 一次删除上千个文件会被系统拦

清理输出目录时，单个目录下上千个文件，超过批量删除阈值，直接被安全策略拒绝。

处理：改成逐条 `os.remove` 或先移到临时目录。

## 七、输出与可溯源

每张图都保留来源与落盘路径，便于回溯：

- `manifest.csv`：机构级清单（名称、POI ID、分类、地址、电话、经纬度、照片数、已下载、最大尺寸、抓取日期、目录）

## 八、挑图：像素之外还该看什么

### 只看像素会挑错

一个门店的十来张图里，通常混着门头、店内环境、菜品、菜单、甚至顾客照片。按像素取最高的那张，很可能是一张菜品特写——分辨率完美，用途为零。而配图要的恰恰是正门头。

这不是精度问题，是**指标选错了**：像素衡量的是「这张图有多大」，而需求是「这张图拍的是什么」。前者可以从文件头读到，后者需要理解图像内容。

### 三个不用模型的弱特征

在没有内容识别的前提下，有三个便宜的替代信号：

| 特征 | 观察 | 代价 |
|---|---|---|
| 构图 | 门头照多为横构图（宽 ≥ 高），菜品、人像、菜单多为竖构图 | 读文件头即可 |
| 相册顺序 | 门头照多排在相册前几张，菜品在后 | 看文件名序号 |
| 像素档 | 商户上传原图与平台缩略图混在相册里，原图通常明显更大 | 已有的尺寸 |

排序键按这个顺序组合：**先按像素分档（25 万像素/档），同档内再看构图与顺序**。分档在前是关键——否则一张 500px 的横图会挤掉一张 4000px 的竖图，为了构图牺牲清晰度，得不偿失。

`best/_report.csv` 的「入选理由」列会写明这一张是按哪个条件选中的。

### 为什么不上图像识别

上模型意味着新增依赖（几百 MB 运行时）、新增一个不可控环节（模型判错时无从追究），而对「门头 vs 菜品」这种二分类，收益远不如把工作量转嫁给人的眼睛：

- 总览图每店并排三张，同一格内就有备选，扫一眼就能定
- 挑错了也不会满盘皆错，因为下一张就在旁边

真要做内容筛选，正确的做法是先有标注集再谈模型，而不是先接一个模型进来碰运气。

## 九、两个必须记住的限制

### 1. 没有拍摄时间

接口不返回照片的拍摄日期。`manifest.csv` 里的「抓取日期」是**采集当天**的时间，含义是「这张照片反映的是这一天库内的状态」，与照片何时拍摄无关。

后果：门店换招牌、搬迁、倒闭，照片都不会自动更新。用于核对门头时，五年前的照片和上周的照片在数据里长得一模一样。要么人工判断，要么接受这个不确定性并在结论里写明。

### 2. 失效是静默的

| 外部变更 | 表面现象 | 实际后果 |
|---|---|---|
| `limit_1` 被忽略 | 下载成功，退出码 0 | 全是 500px 缩略图 |
| `region` 写法不被接受 | 有结果返回 | 静默退化为全国搜索，结果串到别的城市 |
| 百度相册结构变化 | 解析出 0 张图 | 当成「该店没照片」跳过 |

三种情况表现都是「看起来正常」。崩溃会被人发现，静默失效会进报告——所以 `cli.py` 抓完会打印中位分辨率，`probe.py` 可以放进定时任务，专门盯第一条。
